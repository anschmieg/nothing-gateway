# CPA plugins, canonicalization, and smart routing: discussion recap

This recap covers the November 23, 2026 [Replace Custom Canonicalization Logic](t3-thread://v2/71eb682a-3dc3-4413-83cc-e028e12f207c/0188b50b-4ee2-43fd-aee2-7e27de5f254b) thread. Status statements describe what the thread recorded, not a fresh check of production.

The discussion began as a research-first review of what CLIProxyAPI (CPA) plugins could replace. It then branched into building a non-Codex OpenAI Responses provider and diagnosing why canonical-only routing blocked it on `fra`.

## Canonicalization and plugin strategy

1. **Could `DoingDog/cpa-plugin-model-mapper` replace custom canonicalization?** It can handle fixed request aliases, but not the whole policy. The mapper sends an alias to one configured target and can restore the client-facing name in supported responses; it leaves `/v1/models` alone. Gateway canonicalization publishes one ID for multiple verified provider routes, deduplicates discovery, and applies eligibility, pricing, cooldowns, and fallback rules. A `:free` request can try multiple eligible free routes without making paid routes eligible. `gateway.routes.yaml` already handles fixed aliases. Endpoint-specific or per-client aliases were a potential reason to use the mapper.
2. **Could more custom gateway code move into CPA plugins?** The recommendation was to start with usage accounting and quota reporting, and continue moving provider-specific login, refresh, registration, and execution into plugins, as with Cline and OpenCode. CPA's model router can help select a target; its scheduler can choose eligible credentials. The public gateway still needs to own the cross-backend catalog and usage aggregation, specialist endpoints such as SystemOne and Mistral realtime, and guarantees the hooks don't fully cover: global deduplication, dispatch-time price checks, and a shared fallback retry budget. The suggested first experiment was to shadow the Codex OAuth usage observer and compare streaming, non-streaming, and cache-token accounting before switching.
3. **Collect everything possible through existing or custom plugins and turn it into a structured plan before implementing anything.** The plan had to reflect the actual gateway and native CPA capabilities. The user separately asked that both their requests and the assistant's interpretation be recorded in the repo before work began. The [gateway plugin evaluation plan](gateway-plugin-evaluation-plan.md) was written and linked from the existing backlog. It distinguished the public Node gateway with embedded CPA `v7.3.20` from the separate patched CPA `v8.0.49` deployment: moving something into a v8 plugin does not necessarily retire its Node implementation.

## Coolify and the official OpenAI API

4. **Would a Cloudflare Worker speed up the Docker gateway, and where should the official OpenAI API be added in CPA?** A Worker might help lightweight or direct-to-upstream routes, but would add a hop where CPA is still needed. After finding that `PlaygrndLabs/sub2api` still uses a container on Cloudflare, the user decided to stay on Coolify. The initial recommendation was **Providers → OpenAI Compatible**, which uses upstream Chat Completions rather than native Responses.
5. **Could OpenAI be added as a Responses provider instead? Were CPA and CPAMC current, and did they update automatically?** The repo recorded patched CPA `v8.0.49` and CPAMC `v1.27.0`. The thread verified upstream `v8.1.1` and `v1.29.1` on November 23, 2026, but couldn't independently confirm the protected live versions. Coolify ran a pinned binary from a mount and panel auto-updates were off. The first Responses option discussed was CPA's Codex API-key connection, but it rewrites requests and can strip `previous_response_id`.
6. **Would using the ChatGPT Pro API allowance through CPA's Codex API-key connection violate the Codex exclusion even if the actual gateway client wasn't Codex?** The thread didn't establish how OpenAI would classify that proxy path. The recommendation was to keep the Pro API key on a standard Responses route for non-Codex clients and keep Codex on the separate ChatGPT OAuth lane.
7. **Could CPA support Responses providers natively or via a plugin? Was there an existing plugin with a user-defined base URL? Should the deployment carry the upstream PR or use a small plugin?** CPA PR `#5382` proposed `wire-api: responses`, but it hadn't shipped in the versions checked. The Ollama plugin accepted a configurable URL but used Ollama-specific key validation and discovery; the DeepSeek plugin used fixed endpoints. No drop-in for an OpenAI project key was verified. A separate provider plugin was recommended over carrying an unmerged patch to shared executor, auth, and streaming code.

## Build, deployment, and credentials

8. **Write the plugin now: keep it simple, support Responses features fully, optimize caching without breaking upstream caches, and don't send a Codex signature to OpenAI.** The [plugin](https://github.com/anschmieg/cpa-openai-responses/tree/v0.3.0) passed through streamed and buffered creation, compaction, hosted tools, `previous_response_id`, and cache controls while preserving prompt prefixes and tool order. It built fresh upstream headers, rejected known Codex client markers, and only replayed opaque state from the same upstream for the same authenticated caller. Mock tests passed. Full API parity was not achieved: stored-response retrieval, cancellation, deletion, input-item listing, and native upstream WebSockets still needed host routes.
9. **Was it already live? If not, deploy it. Also upgrade CPA and CPAMC immediately and set up automatic updates for both.** The plugin passed local tests on CPA `v8.1.1`, and a CPAMC `v1.29.1` build with the Cloudflare Access patch passed local tests. SSH to `fra` was rejected, and the full CPA patchset still needed to be ported before replacing the live binary. No live upgrade or auto-update setup was confirmed.

The OpenAI project key should be entered in CPAMC, like other providers. The replacement Coolify token worked, but control-plane access did not grant write access to the bind mount. A patched panel with a masked key field was built locally, not deployed.
11. **Provide an SCP bundle or use the T3 Code link to `fra`; T3 Code on `fra` has read/write/execute access to `/data/*`.** The assistant confirmed `fra` was linked and packaged a credential-free bundle. The registry was `https://raw.githubusercontent.com/anschmieg/cpa-openai-responses/main/registry.json`. The user then installed the plugin and saved the key.

## Credit grants, canonical routing, and release reconciliation

14. **Use OpenAI's organization Credit Grants data for routing decisions.** The documented design favored the non-Codex Responses route while eligible credits remained, accounted for cached-token pricing and in-flight spend, and required an explicit pay-as-you-go profile when the balance was stale, depleted, or expired. The first design used a manually entered snapshot because the Costs API reports spend rather than remaining grants. Live routing weights didn't change.
15. **Investigate the issue reported on `fra`, and fetch the user's remote changes to produce one valid release, cleaning up Git history if needed.** The rebuilt plugin loaded, but `/v1/models` showed no `openai-responses/…` models. Explicit `openai-responses/gpt-4.1-mini` requests returned `503` with “no eligible route satisfies model and billing policy” even under `PAID`; the user's direct OpenAI request using the same key returned `200`. With `canonical-only` off, the model appeared and the mock request worked. With it on, no request reached the mock upstream. The shared model refresh interval was 60 minutes, and canonical-only routing and billing defaults were unchanged. The expected behavior was discovery and dispatch for an explicitly authorized plugin route without weakening billing or falling back to another provider.
16. **The user confirmed that the missing changes had been rebased and pushed.** The assistant found the upstream model-discovery commit on top of the credential fix and published `v0.3.0` with both, preserving the existing history and tags. The tagged source reproduced the ARM64 binary byte for byte and passed Plugin Store and mock HTTPS tests on CPA `v8.0.49` and `v8.1.1`. The thread didn't record deploying this release to `fra`. The release didn't fix the `503`: the host registered static plugin models under a synthetic catalog entry without a canonical route binding or auth record, and the billing planner ran before the plugin routing hook. See the [canonical routing issue report](openai-responses-canonical-routing-issue.md).
17. **“indeed. fix that now!”** The last visible update said the separate CPA host fix was underway, with mock-upstream checks planned for discovery, dispatch, and billing rejection. No completed or deployed host fix was recorded when the thread was read.
