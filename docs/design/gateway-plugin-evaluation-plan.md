# Gateway plugin and deployment evaluation

The public Node gateway owns the unified catalog, routing across backends, and specialist endpoints. Its Docker image embeds CLIProxyAPI (CPA) v7.3.20 for OAuth. The separate CPA v8.0.49 line has OpenCode and Cline plugins, a pinned Free Model Hub integration, and host patches for catalog and canonical routing. A feature moved to a plugin only applies to requests that go through that CPA host. Evaluate both hosts separately and record which gateway code could actually be retired.

This is the research plan for the requested inventory. Implementation, provider enrollment, and deployment follow separately. Repository descriptions below identify candidates to investigate. Confirm behavior from source before treating any candidate as a fit. The [earlier plugin reference backlog](gateway-plugin-reference-backlog.md) is also an input where its candidates overlap.

## Official OpenAI API provider

For a Responses upstream on CPA v8, use **Providers → Codex → API-key connection** in CPAMC. The config section is `api-keys.codex`. Use a separate group such as `openai`, set the base URL to `https://api.openai.com/v1`, and enter the OpenAI project key and exact upstream model IDs. A prefix such as `openai` gives the paid route its own namespace. Keep it separate from the ChatGPT subscription OAuth lane and free-only routing. The Codex executor sends generation to upstream `/responses`. [CPA v8 example config](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.49/config.example.yaml#L677) · [Codex executor](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.49/internal/runtime/executor/codex_executor_execute.go#L65)

The Codex executor applies its own request translation and removes `previous_response_id` on the HTTP execution path. Check stateful continuation and any Responses features the client depends on before choosing this route. Ordinary generation through **OpenAI Compatible** instead goes to upstream `/chat/completions`. Adding either connection on the separate native host requires an explicit routing and catalog decision for any public gateway that uses a different backend. [OpenAI-compatible executor](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.49/internal/runtime/executor/openai_compat_executor.go)

For subscription-granted API credits, OpenAI explicitly covers Responses API usage and excludes Codex usage through API keys. The published benefit does not clarify how a third-party proxy using its Codex executor is classified. Keep those credits on a standard API route for non-Codex callers, using Chat Completions via OpenAI Compatible or direct Responses via a dedicated passthrough. Keep Codex clients on the separate subscription lane. [OpenAI API credits for ChatGPT subscribers](https://developers.openai.com/api/docs/guides/chatgpt-api-credits#what-the-credits-cover)

### OpenAI credit grants in routing

Use the linked OpenAI API organization's [Credit grants page](https://platform.openai.com/settings/organization/billing/credit-grants) as the source for an operator-supplied balance snapshot. Confirm the organization matches the Responses project key. Record the remaining eligible amount in USD, observation time, and expiration for each grant as shown. OpenAI says unused subscription credits expire at the end of the billing cycle. The documented organization Costs endpoint provides spend by time bucket and can group by project. It does not provide a grant balance or establish which charges a grant covered. [OpenAI API credits](https://developers.openai.com/api/docs/guides/chatgpt-api-credits) · [Organization Costs API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs)

Use a fresh snapshot to admit or raise the priority of the non-Codex OpenAI Responses route in profiles that allow credit-backed providers. Subtract estimated eligible spend since the snapshot using actual route usage and model rates, including cached input rates, and reserve estimated spend for in-flight requests. Keep this budget shared across keys in the same organization. Preserve session affinity while the route remains eligible so credit weighting does not needlessly break prompt caching. If the balance is stale, depleted, or expired, remove the credit-backed preference and allow the route only under an explicitly pay-as-you-go profile. Treat spend-based balances as estimates, since delayed reporting or usage outside the gateway can consume the same grants.

The dashboard requires a signed-in billing session. No supported automatic grant balance feed was verified. Start with operator-supplied snapshots and validate admission in shadow mode before changing live weights.


CPA's generic native Responses option, `openai-compatibility[].wire-api: responses`, is proposed in open upstream PR #5382. It is absent from the pinned v8.0.49 and the checked v8.1.1 release. Evaluate the released native option when available. For the current host, evaluate a small provider plugin using the `openai-response` executor format and the host HTTP callbacks to call the configured upstream `/responses` endpoint. The DeepSeek and Ollama plugins show this pattern with their respective providers. This search did not find a verified drop-in plugin for official OpenAI project keys. A mock-host check should cover model selection, buffered and streamed responses, stateful continuation, hosted tools, cancellation, and upstream errors. Keep compact and WebSocket support as explicit compatibility checks. [Upstream proposal](https://github.com/router-for-me/CLIProxyAPI/pull/5382) · [DeepSeek executor](https://github.com/xspeed1989/cpa-plugin-deepseek/blob/main/executor.go) · [Ollama executor](https://github.com/azwildfire/cliproxyapi-ollama-plugin/blob/main/internal/provider/executor.go)

The Ollama plugin accepts a custom `base_url` and sends generation to `/v1/responses`, but API-key validation calls Ollama's `/api/me` and model discovery calls `/api/tags`. Those dependencies prevent a base-URL-only repoint to OpenAI. The DeepSeek plugin uses fixed DeepSeek endpoints. [Ollama credential validation](https://github.com/azwildfire/cliproxyapi-ollama-plugin/blob/main/internal/provider/client.go) · [Ollama model discovery](https://github.com/azwildfire/cliproxyapi-ollama-plugin/blob/main/internal/provider/models.go) · [DeepSeek executor](https://github.com/xspeed1989/cpa-plugin-deepseek/blob/main/executor.go)

## Deliverable and order

1. Map each feature to its current owner and the native configuration or hook available on each CPA host. Begin with routing, quotas, refresh, and affinity so the cache comparison uses the same assumptions.
2. Inspect the listed repositories, public `ahoo` CPA repos, and relevant earlier references. Record the release or commit, hook, host version tested or verified, credential access, external calls and background activity, protocol and streaming coverage, and code that could be retired. Cover OpenCode, the free providers, Copilot, AWS, and OpenAI in the provider pass. Evaluate compaction, vision, and reasoning summaries together because each can alter conversation state or add inference.
3. For unresolved plugin behavior, identify the smallest mock-host check that would settle it. Confirm account-dependent entitlements separately from source claims.
4. Deliver a ranked inventory with one disposition per feature: native config, adopt an existing plugin, adapt one, write a custom plugin, retain gateway or host code, or defer pending evidence. Include the expected benefit, evidence, dependencies, and unresolved questions. Use that inventory to choose implementation work.
